# 디자인 하네스 설계 문서

디자인 작업을 AI에게 맡길 때 쓰는 Claude Code 플러그인의 설계다. 아직 코드는 없고, 이 문서가 구현의 기준이 된다.

## 1. 목적

- 디자인 작업을 정해진 단계로 나눠 AI가 한 단계씩 진행하게 한다.
- 단계마다 남는 파일을 정해 두어, 사람이 언제든 진행 상황을 파일로 확인할 수 있게 한다.
- 다음 단계로 넘어가는 조건을 명시하고, 판단이 필요한 지점에서는 사람의 승인 없이 넘어가지 않게 한다.

다루지 않는 것: 실제 프론트엔드 구현, 배포, 디자인 툴 자체의 대체.

## 2. 단계 개요

```
PRD → 리서치 → 화면 구조 → 와이어프레임 → 디자인 시스템 → 피그마 → 검증 → 핸드오프
```

순서대로 진행하며, 앞 단계의 산출물이 뒤 단계의 입력이 된다. 뒤 단계에서 앞 단계의 문제가 발견되면 해당 단계로 되돌아간다(6장).

## 3. 산출물 위치

모든 산출물은 **하네스를 쓰는 프로젝트**의 `work/<프로젝트>/` 아래에 둔다. 플러그인 폴더에는 아무것도 쓰지 않는다.

```
work/<프로젝트>/
├── state.json              # 현재 단계, 단계별 상태, 승인 기록
├── 01-prd/
│   ├── prd.md
│   └── open-questions.md
├── 02-research/
│   ├── research.md
│   ├── references/         # 참고 화면 캡처(links.md → *.png, captures.json), 링크 목록
│   └── insights.md
├── 03-ia/
│   ├── sitemap.md
│   ├── screens.md          # 화면 목록 (ID, 목적, 진입 경로, 관련 요구사항)
│   └── flows.md            # 주요 사용자 흐름
├── 04-wireframe/
│   ├── <화면ID>.md         # 화면별 구성 요소와 배치 설명 (## 레이아웃, ## 상태: <이름>)
│   └── <화면ID>.svg        # 저충실도 와이어프레임 (md 에서 생성)
├── 05-design-system/
│   ├── tokens.json         # 색, 타이포, 간격, 반경, 그림자
│   ├── components.json     # 컴포넌트 목록과 상태(variant)
│   ├── copy.json           # 용어, 금지 문구, 메시지
│   ├── DESIGN.md           # 위 세 JSON 에서 생성한 정리본
│   └── principles.md
├── 06-figma/
│   ├── figma.json          # 쓰기 대상 Figma 파일 (fileUrl 또는 fileKey) — 이 파일에만 쓸 수 있음
│   ├── figma.md            # 파일 URL, 페이지 구성
│   ├── node-map.json       # 화면ID/컴포넌트 ↔ Figma 노드 ID
│   └── nodes/*.json        # 내보낸 노드 (REST API 노드 JSON) — lint:figma 검사 대상
├── 07-verify/
│   ├── report.md           # 검증 결과 요약
│   └── issues.md           # 발견 문제, 심각도, 되돌릴 단계
└── 08-handoff/
    ├── HANDOFF.md          # 개발자용 안내서 (생성)
    ├── specs/<화면ID>.md   # 화면별 상세 스펙
    └── tokens/             # 플랫폼별 토큰 내보내기 (css, json 등)
```

번호 접두어는 단계 순서를 폴더 정렬로 보이게 하기 위한 것이다.

## 4. 단계별 산출물·통과 조건·승인

| # | 단계 | 만들어지는 파일 | 다음 단계로 넘어가는 조건 | 사람 승인 |
|---|------|----------------|--------------------------|-----------|
| 1 | PRD | `01-prd/prd.md`, `01-prd/open-questions.md` | 목표, 대상 사용자, 핵심 요구사항(ID 부여), 범위 밖 항목, 성공 기준이 모두 채워짐. `open-questions.md`에 미해결 질문이 없거나 "보류"로 표시됨 | **필요** — 요구사항과 범위 확정 |
| 2 | 리서치 | `02-research/research.md`, `references/`, `insights.md` | 경쟁/참고 사례 최소 3개 분석, 각 인사이트가 PRD 요구사항 ID와 연결됨. 출처 없는 주장 없음 | 불필요 (요약만 보고) |
| 3 | 화면 구조 | `03-ia/sitemap.md`, `screens.md`, `flows.md` | PRD의 모든 요구사항 ID가 하나 이상의 화면에 매핑됨. 모든 화면에 진입 경로가 있음(고립 화면 없음). 주요 흐름이 끝까지 이어짐 | **필요** — 화면 목록과 흐름 확정 |
| 4 | 와이어프레임 | `04-wireframe/<화면ID>.md`, `<화면ID>.svg` | `screens.md`의 모든 화면에 와이어프레임 존재. 빈 상태·오류·로딩 상태가 필요한 화면은 해당 상태 포함 | **필요** — 레이아웃 방향 확정 |
| 5 | 디자인 시스템 | `05-design-system/tokens.json`, `components.json`, `copy.json`, `DESIGN.md`, `principles.md` | 와이어프레임에 쓰인 모든 요소가 컴포넌트 목록에 있음. 텍스트/배경 색 조합이 WCAG AA 대비 기준 충족. 세 JSON 스키마 검사 통과, `DESIGN.md`가 JSON 내용과 일치 | **필요** — 시각 방향(색, 타이포) 확정 |
| 6 | 피그마 | `06-figma/figma.json`, `figma.md`, `node-map.json`, `nodes/` | 토큰이 Figma 변수/스타일로 등록됨. 모든 화면ID와 컴포넌트가 `node-map.json`에 노드 ID로 연결됨 | 불필요 (검증 단계에서 함께 확인) |
| 7 | 검증 | `07-verify/report.md`, `issues.md` | `issues.md`에 "차단" 심각도 문제가 0건. 나머지 문제는 수정 또는 "수용"으로 표시됨 | **필요** — 결과 확인과 남은 문제 수용 여부 결정 |
| 8 | 핸드오프 | `08-handoff/HANDOFF.md`, `specs/`, `tokens/` | 모든 화면에 스펙 존재, 토큰 내보내기 완료, 스펙의 Figma 링크가 유효함 | **필요** — 최종 인수 |

내보낸 Figma 노드는 `lint:figma`로 토큰 밖 색·글자 크기·글꼴·간격, 44px 미만 인터랙티브 요소, 금지 문구, variant 누락을 검사한다. 화면 HTML 이 있으면 `lint:web`으로 토큰 밖 색·글자 크기, 44px 미만 버튼, `copy.json` 금지 문구를 검사한다(검증 단계의 자동 항목 일부). 사람 검토 점수는 단계 진행을 막지 않는 기록으로 `work/<프로젝트>/reviews.json`에 쌓는다.

### 승인 원칙

- 승인은 사람이 명시적으로 해야 한다. AI가 스스로 승인 상태로 바꾸지 않는다.
- 승인 기록은 `state.json`에 남긴다: 승인한 사람, 시각, 승인 시점 산출물의 해시, 메모.
- 승인 후 해당 단계 산출물이 바뀌면(해시 불일치) 승인이 무효가 되고 재승인이 필요하다.
- 승인이 불필요한 단계도 단계 종료 시 요약을 사람에게 보여준다. 사람이 원하면 그 자리에서 멈출 수 있다.

## 5. 검증 단계 세부 항목

검증은 자동 검사와 AI 리뷰로 나눈다.

| 구분 | 항목 | 기준 |
|------|------|------|
| 자동 | 요구사항 추적 | PRD 요구사항 ID → 화면 → Figma 노드까지 끊김 없음 |
| 자동 | 토큰 사용 | Figma 노드의 색·글꼴·간격이 토큰 외 값을 쓰지 않음 |
| 자동 | 대비 | 텍스트 대비 WCAG AA (일반 4.5:1, 큰 글씨 3:1) |
| 자동 | 터치 영역 | 인터랙티브 요소 최소 44×44pt |
| 자동 | 상태 누락 | 컴포넌트별 정의된 variant(기본/호버/비활성/오류 등)가 Figma에 존재 |
| AI 리뷰 | 와이어프레임 대비 변경 | 승인된 와이어프레임과 다른 부분 목록화, 의도된 변경인지 표시 |
| AI 리뷰 | 문구 | 용어 일관성, 오류 메시지 안내성 |

문제마다 심각도(차단/주요/경미)와 되돌릴 단계를 `issues.md`에 적는다.

## 6. 되돌아가기

- 어느 단계에서든 앞 단계의 문제가 발견되면 `state.json`의 현재 단계를 해당 단계로 되돌린다.
- 되돌아간 단계와 그 뒤 모든 단계의 승인은 "재확인 필요"로 바뀐다. 산출물은 지우지 않고 유지한다.
- 되돌아간 이유는 해당 단계 폴더의 `changelog.md`에 남긴다.

## 7. 플러그인 구성

```
design-harness/                 # 이 저장소 = 플러그인
├── .claude-plugin/plugin.json
├── commands/
│   ├── design-start.md         # 프로젝트 생성: work/<프로젝트>/ 와 state.json
│   ├── design-next.md          # 현재 단계 진행 또는 다음 단계로 이동 시도
│   ├── design-status.md        # 단계별 상태·승인·미해결 문제 표시
│   ├── design-approve.md       # 사람이 현재 단계 승인 (해시 기록)
│   └── design-back.md          # 지정 단계로 되돌아가기
├── skills/
│   ├── prd/  research/  ia/  wireframe/
│   ├── design-system/  figma/  verify/  handoff/
│   │   └── SKILL.md            # 단계별 작업 지침, 산출물 템플릿, 통과 조건
├── agents/
│   ├── researcher.md           # 리서치 전담 (웹 검색 사용)
│   └── reviewer.md             # 검증 단계 AI 리뷰 (작성자와 분리된 시각)
├── hooks/
│   └── hooks.json              # 단계 게이트 강제
└── scripts/
    ├── check-gate.*            # 단계별 통과 조건 검사
    ├── contrast.*              # 대비 계산
    └── hash-stage.*            # 산출물 해시
```

### 게이트 강제 방식

- `/design-next`는 이동 전에 `check-gate`를 실행한다. 조건 미충족 시 어떤 항목이 빠졌는지 보여주고 멈춘다.
- 승인이 필요한 단계는 `state.json`에 유효한 승인이 없으면 이동하지 않는다.
- `PreToolUse` 훅으로 아직 열리지 않은 단계 폴더(`work/<프로젝트>/0N-*/`)에 쓰는 것을 막는다. 앞 단계를 건너뛰고 산출물을 만드는 것을 방지한다.
- `state.json`의 승인 필드는 `/design-approve`를 거쳐서만 바뀌도록, 직접 편집도 훅으로 막는다.
- Figma MCP 쓰기 도구는 `PreToolUse` 훅이 호출 직전에 검사한다. 도구 입력의 파일 키가 `06-figma/figma.json`의 파일이고 피그마 단계가 열렸을 때(디자인 시스템까지 승인)만 통과한다. 파일 키를 알 수 없는 쓰기도 막는다.
- Figma 쓰기 뒤에는 `PostToolUse` 훅이 바뀐 노드를 `06-figma/nodes/`에 다시 내보내고 `lint:figma`를 돌리라고 알린다.
- 답을 끝낼 때 `Stop` 훅이 `check`를 돌려 프로젝트별 현재 단계와 빠진 것을 사람에게 보여 준다. 답을 막지는 않는다.

### state.json 형태 (안)

```json
{
  "project": "<프로젝트>",
  "currentStage": "ia",
  "stages": {
    "prd": {
      "status": "approved",
      "approval": { "by": "<이름>", "at": "2026-10-27T15:00:00+09:00", "hash": "sha256:...", "note": "" }
    },
    "research": { "status": "done" },
    "ia": { "status": "in_progress" }
  }
}
```

단계 상태: `not_started` → `in_progress` → `done`(조건 충족) → `approved`(승인 필요 단계만). 되돌아가면 `needs_recheck`.

## 8. 외부 의존

- **Figma**: Figma MCP 서버로 파일 읽기/쓰기. 쓰기 권한이 없는 환경이면 피그마 단계는 "사람이 직접 만들고 AI가 `node-map.json`만 작성"하는 모드로 진행한다.
- **웹 검색**: 리서치 단계에서만 사용.
- 외부에 산출물을 게시하는 동작은 하지 않는다. Figma 쓰기 외에는 모두 로컬 파일로 남긴다.

## 9. 미정 사항

- 와이어프레임 형식: SVG 직접 생성 vs. 텍스트 레이아웃 기술만 두고 Figma에서 처음 그리기.
- 디자인 시스템이 이미 있는 프로젝트에서 5단계를 "가져오기"로 대체하는 방법.
- 여러 사람이 승인하는 경우(디자이너, PM)의 승인 정책.
- 큰 프로젝트에서 화면 단위로 4~7단계를 부분 진행할지 여부.
